# Issue #1 実装と検証

この文書は設計案と実装を区別するための記録です。実機カメラ・長時間運用の互換性を保証するものではありません。

## モジュール境界

- `recorder_app/inputs.py`: RTSP/TCP、RTMP Listen引数と任意の短時間入力検査。
- `configuration.py`: v1/v2正規化と移行用設定の生成。
- `controls.py`: 機能宣言、制御factory、Genericの停止済みAEサービス。
- `kn20a.py`: 従来のHTTP/VISCAクライアントを移植。露出の計算・設定値は変更していません。
- `preparation.py`: 非同期準備、送信直前の予約・世代・期限検証、録画占有、手動操作との競合管理。
- `artifacts.py`: 原本検査、互換group、全体検証、永続manifest、cleanupと再開。
- `recorder.py`: 既存CLI/APIとクラス名を互換入口として残し、上記サービスを構成します。設計案のすべてのクラスを別ファイルへ分けることはしていません。

## レビュー対応

| 指摘 | 実装 |
| --- | --- |
| R01 原本削除 | 既存MP4を存在/durationだけで信用しない。未検証出力を退避。入力/出力hash、packet数、全frame形状・デコード、対応groupのmanifestを検証し、削除許可を永続化してから原本を削除。旧分割MP4にも同じ条件を適用 |
| R02 中断後復旧 | ScheduleStore読込では録画中の証拠をpendingへ変換しない。起動時に終了済み予約の残存原本・manifestを照合して後処理へ投入。再接続待ちのまま予約が終了した場合も後処理へ投入 |
| R03 次予約の画角変更 | 録画・再接続待ち中はカメラ所有者を保持。別予約の準備をdefer。接続後のsendall直前にも予約revision・generation・期限・所有者を検証。送信済み結果が不明なら保留し、再起動を跨いで未確定状態を復元 |
| R04 旧予約の契約 | policy欠落はlegacy。新規予約はpolicy・期限・制御資源を作成時に保存。後日の設定変更で保存済み契約を変更しない |

新規設定はGeneric＋原本保持＋continueを既定にしています。schema_versionのない設定は従来のKN20Aとして処理します。任意の入力検査は追加接続できないカメラ向けにOFF可能で、録画開始に優先権を渡します。

### PR #2 の追加レビュー対応

- 手動プリセットも、予約ファイルと同じ場所の `schedules.control.json` に送信前の実行中状態を永続化します。正常完了時だけ解除し、例外・プロセス終了・再起動を跨いだ結果未確定状態は既存の明示確認APIで解除するまで制御を保留します。保存に失敗した場合は送信しません。
- `preparing` manifestの部分成功も復旧対象です。原本集合・hashが一致することを先に確認し、groupの対応、出力hash、メディア検証が一致する完成済みMP4は再利用します。原本変更時は再利用・削除を禁止し、出力だけが壊れていた場合はそのgroupを再生成します。全group完了前には原本を削除しません。
- 回帰試験には手動操作中の実プロセス強制終了と再起動、明示解除後の自動制御再開、複数groupの部分失敗・繰り返し復旧、原本／出力改変を含めます。

## 検証方法

`tests/test_issue1.py` はレビュー由来の回帰、`tests/test_platform.py` はOS差、既存 `test_recorder.py` とAEシミュレーションは従来の機能を検証します。ローカルWindows/Python 3.10とUbuntu 24.04/Python 3.12、GitHub Actionsの6 matrixを使用します。

`tools/investigate_issue1.py --assert-network` は、MediaMTX v1.21.2と生成映像を使ったloopback内のRTSP/RTMP予約、再接続、分割、後処理を確認します。ネットワーク試験は別CI jobで、公式アーカイブをchecksum照合して取得します。実機へ接続しません。

接続断で生成ファイルが破損する場合、再接続試験では「検証済み出力」か「明示的な後処理失敗＋原本保持」を正常な保護動作として認めます。後者を「録画全体が欠落なく成功」とは報告しません。

調査資料の古い数値・現行コードという記述は、調査対象コミットに対する所見です。ハーネスは現在の作業ツリーを読み込むため、修正後は破損出力の検証結果や復旧結果が変わります。

## 制約

- ONVIF/SRTや複数カメラは未実装。KN20A以外の露出制御も未提供です。
- 全frame検査・全体デコードは長時間録画でCPUと時間を使用します。検証失敗・timeout・容量不足時は原本を保持します。
- 送信済みの物理移動の完全取消は保証しません。結果未確定時は画面で確認・解除が必要です。
- 壊れた原本を無断で除外・再エンコードして完了扱いにはしません。
- 原本とmanifestはアプリが管理するフォルダで運用してください。別プロセスが同時にファイルを書き換える運用は対象外です。
